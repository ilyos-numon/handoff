# 3역할 통합 시연 시나리오 (브라우저 3창, 20단계)

## 데모 모드로 바로 보기

준비 단계와 브라우저 3개 없이 보려면 데모 모드를 쓴다. API 키는 필요 없다.

```bash
cd handoff
make demo        # "데모 주소: http://localhost:8780/demo" 가 출력된다
```

1. 브라우저로 `/demo` 를 열면 바로 나만의 연습 공간(24시간 유지)이 생기고 팀장·퇴사자·후임 화면이 한 페이지에 나란히 뜬다.
2. 아래 1~10단계(모의 자료 불러오기·질문 만들기·사전 부검·우선 질문·세션 1회 답변과 종료)는 미리 채워져 있다.
3. **11단계부터** 이어서 하면 된다. 후임 화면에서 11단계 질문을 넣으면 세션 1의 답이 근거와 함께 나온다.

데모 모드는 녹화된 답을 재생하고 업무 자료 업로드를 막는다. 설정은 [usage.md 데모 모드](usage.md#데모-모드).

팀장이 먼저 물어볼 질문을 정하고, 퇴사자가 세션에서 답하고, 후임이 그 답을 근거와 함께 찾아보고, 후임이 모르는 질문은 다시 퇴사자에게 돌아가는 흐름을 화면 3개로 확인한다. 역할 밖 화면과 API는 막혀야 한다.

이 문서의 입력 문장·버튼·기대 문구는 `tests/e2e/test_demo_scenario.py` 가 그대로 따라가며 검증한다. 단계마다 그 테스트가 남기는 스크린샷 이름(`demo-NN-<slug>.png`)을 적어 두었다.

## 준비

1. 깨끗한 데이터 폴더로 서버를 띄운다. 기본 공급자(`fake`)와 인증 켜짐이 기본값이다. 아래 기대 결과(질문 수·항목 수)는 빈 데이터 폴더 기준이다.

   ```bash
   cd handoff
   rm -rf ./demo-data
   HANDOFF_DATA_DIR=./demo-data uv run uvicorn handoff.main:create_app --factory --port 8780
   ```

2. 다른 터미널에서 초대 링크 3개를 만든다. 서버와 **같은** `HANDOFF_DATA_DIR` 를 줘야 서명 키가 맞는다. 각 명령은 링크 한 줄을 출력한다.

   ```bash
   HANDOFF_DATA_DIR=./demo-data uv run python -m handoff.rbac.cli invite --role manager --leaver kim
   HANDOFF_DATA_DIR=./demo-data uv run python -m handoff.rbac.cli invite --role leaver --leaver kim
   HANDOFF_DATA_DIR=./demo-data uv run python -m handoff.rbac.cli invite --role successor --leaver kim
   ```

   링크는 `http://localhost:8780/auth/accept?token=...` 모양이고 72시간 동안 쓸 수 있다.

3. 창 3개를 연다. 로그인 쿠키가 섞이지 않도록 창마다 쿠키 저장소가 달라야 한다.
   - **팀장 창**: 브라우저 A 일반 창
   - **퇴사자 창**: 브라우저 A 시크릿 창
   - **후임 창**: 브라우저 B (다른 브라우저 또는 다른 프로필)

   같은 브라우저의 일반 창 두 개는 쿠키를 공유하므로 쓰지 않는다. 링크를 연 창은 마지막으로 연 링크의 역할이 된다.

## 단계

### 단계 1 — 팀장 창 초대 링크 열기

- 행동: 팀장 초대 링크를 주소창에 붙여 넣는다.
- 기대 결과: 주소가 `http://localhost:8780/report` 로 바뀐다. 제목 `인수인계 진행 상황 · 세션 0/10 기준`. 축 4개(담당 시스템·반복 업무·사고 이력·관계자)가 모두 `0/10`. 오류 상자 없음.
- 스크린샷: `demo-01-manager-report-empty.png`

### 단계 2 — 팀장 창 모의 업무 자료 불러오기

- 행동: `모의 업무 자료 불러오기` (`#sources-mock`) 를 누른다.
- 기대 결과: 버튼 아래 상태 줄(`#report-status`)에 `모의 업무 자료 N건을 불러왔습니다.`
- 스크린샷: `demo-02-manager-sources.png`

### 단계 3 — 팀장 창 자료로 질문 만들기

- 행동: `자료로 질문 만들기` (`#questions-generate`) 를 누른다.
- 기대 결과: 상태 줄 `업무 자료로 질문 N개를 큐에 넣었습니다.` 질문 큐에 `… · 업무 자료 · 대기` 항목들이 생긴다.
- 스크린샷: `demo-03-manager-generated-questions.png`

### 단계 4 — 팀장 창 사전 부검 질문 넣기

- 행동: `사전 부검 질문 넣기` (`#premortem-add`) 를 누른다.
- 기대 결과: 상태 줄 `사전 부검 질문 3개를 큐에 넣었습니다.` 질문 큐에 `· 사전 부검 · 대기` 항목 3개.
- 스크린샷: `demo-04-manager-premortem.png`

### 단계 5 — 팀장 창 우선 질문 지정

- 행동: 입력칸(`#priority-input`)에 아래 문장을 넣고 `우선 질문 지정` (`#priority-send`) 을 누른다.
  > 결제 대행사 장애가 나면 가장 먼저 무엇을 확인하나요?
- 기대 결과: 상태 줄 `우선 질문을 큐에 넣었습니다.` 질문 큐에 `결제 대행사 장애가 나면 가장 먼저 무엇을 확인하나요? · 팀장 우선 · 대기`.
- 스크린샷: `demo-05-manager-priority.png`

### 단계 6 — 퇴사자 창 초대 링크 열기

- 행동: 퇴사자 초대 링크를 연다.
- 기대 결과: 주소가 `http://localhost:8780/` 로 바뀌고 `세션 시작` 버튼을 누를 수 있다. 오류 상자 없음.
- 스크린샷: `demo-06-leaver-entry.png`

### 단계 7 — 퇴사자 창 세션 시작

- 행동: `세션 시작` (`#start-button`) 을 누른다.
- 기대 결과: 머리글 `Handoff · 세션 1/10`, 축 `사고 이력`. 질문 위에 출처 `팀장이 우선 지정한 질문`, 질문은 단계 5의 문장 그대로.
- 스크린샷: `demo-07-leaver-priority-question.png`

### 단계 8 — 퇴사자 창 전화번호가 든 답변

- 행동: 답변 칸(`#answer-input`)에 아래 문장을 넣고 `보내기` (`#send-button`).
  > 결제 대행사 장애가 나면 먼저 대행사 상태 페이지를 확인하고, 담당 엔지니어에게 010-1234-5678 로 전화합니다.
- 기대 결과: `오늘 쌓인 것: 1항목`. 다음 질문은 꼬리 질문 `그렇게 하는 이유는 무엇인가요? 왜 그 방식이 필요한가요?` 이고 출처 표시는 사라진다. (퇴사자 본인 화면에는 자기가 쓴 원문이 그대로 보인다.)
- 스크린샷: `demo-08-leaver-answer-phone.png`

### 단계 9 — 퇴사자 창 답변 2개 더

- 행동: 아래 두 문장을 차례로 넣고 각각 `보내기`.
  > 정산 배치는 매일 새벽 2시에 돌고, 실패하면 아침 9시 전에 수동으로 다시 돌립니다.

  > 금요일 배포는 피합니다. 작년 3월 금요일 저녁 배포 후 정산 배치가 주말 내내 실패했습니다.
- 기대 결과: 첫 문장을 보낸 뒤 나오는 질문의 출처가 `사전 부검 질문`. 두 문장을 다 보내면 `오늘 쌓인 것: 3항목`.
- 스크린샷: `demo-09-leaver-more-answers.png`

### 단계 10 — 퇴사자 창 세션 종료

- 행동: `세션 종료` (`#end-button`).
- 기대 결과: `오늘은 여기까지` 요약 3줄, 첫 줄은 `사고 이력: 결제 대행사 장애가…` 로 시작. `전체 3항목`.
- 스크린샷: `demo-10-leaver-summary.png`

### 단계 11 — 후임 창 초대 링크 열고 아는 질문

- 행동: 후임 초대 링크를 연다(주소가 `/chat` 으로 바뀐다). 질문 칸(`#chat-input`)에 아래 문장을 넣고 `보내기` (`#chat-send`).
  > 결제 대행사 장애가 나면 무엇을 먼저 확인하나요?
- 기대 결과: 답 `인수인계 기록에 따르면: … 담당 엔지니어에게 [전화번호] 로 전화합니다.` 근거 상자 `세션 1 (사고 이력) · 날짜`, 발췌에도 `[전화번호]`. 확신도 `근거 확실`. 화면 어디에도 `010-` 으로 시작하는 번호가 없다.
- 스크린샷: `demo-11-successor-known-answer.png`

### 단계 12 — 후임 창 아무도 답하지 않은 질문

- 행동: 질문 칸에 아래 문장을 넣고 `보내기`.
  > 캐시 서버를 재시작해야 할 때는 어떻게 하나요?
- 기대 결과: 노란 상자에 `이 주제는 인수인계에 없습니다. 팀장에게 확인하세요.` 와 `퇴사자 질문 목록에 올렸습니다. 다음 세션에서 물어봅니다.` 근거 상자 없음. (먼저 물어볼 역할을 아는 경우에만 `먼저 물어볼 역할: …` 줄이 붙는다. 이 시나리오에서는 나오지 않는다.)
- 스크린샷: `demo-12-successor-unknown-queued.png`

### 단계 13 — 후임 창 울타리 질문 (이건 왜 이렇게 되어 있나요?)

- 행동: 아래 칸(`#fence-input`)에 아래 문장을 넣고 `이유 묻기` (`#fence-send`).
  > 금요일 배포 금지
- 기대 결과: `이 결정의 이유는 인수인계 기록에 없습니다.` 아래 `관련 위험:` `작년 3월 금요일 저녁 배포 후 정산 배치가 주말 내내 실패했습니다.` 그리고 `퇴사자 질문 목록에 올렸습니다. 다음 세션에서 물어봅니다.`
- 스크린샷: `demo-13-successor-fence.png`

### 단계 14 — 팀장 창 새로고침

- 행동: 팀장 창을 새로고침한다.
- 기대 결과: 제목 `… · 세션 1/10 기준`. `사고 이력` 행 아래 `추가 질문 2개 답함` (팀장 우선 질문과 사전 부검 질문 1개). 다른 축에는 이 줄이 없다. 질문 큐에 `결제 대행사 장애가 나면 가장 먼저 무엇을 확인하나요? · 팀장 우선 · 답변됨`, `캐시 서버를 재시작해야 할 때는 어떻게 하나요? · 후임 질문 · 대기`.
- 스크린샷: `demo-14-manager-report-progress.png`

### 단계 15 — 팀장 창 빈 구멍 다시 찾기

- 행동: `빈 구멍 다시 찾기` (`#gaps-refresh`).
- 기대 결과: 상태 줄 `빈 구멍 N개, 아무도 확실히 모르는 영역 M개를 찾았습니다.` 빈 구멍 목록에 `메시지 큐 · 위험도 높음` 이 있고 나머지도 `<주제> · 위험도 높음|보통|낮음` 형식. 지금까지 답이 모두 확실한 말투라서 `아무도 확실히 모르는 영역` 은 `찾은 영역이 없습니다.`
- 스크린샷: `demo-15-manager-gaps.png`

### 단계 16 — 팀장 창 운영 런북 만들기

- 행동: 산출물 버튼 중 `운영 런북` (`#artifact-buttons button[data-kind="runbook"]`) 을 누르고, 생긴 `운영 런북` 상자의 `내용 보기` 를 연다.
- 기대 결과: 상태 줄 `산출물을 만들었습니다: 운영 런북`. 본문에 `[전화번호]` 가 보이고 원래 번호는 없다.
- 스크린샷: `demo-16-manager-runbook.png`

### 단계 17 — 퇴사자 창 세션 2

- 행동: 퇴사자 창을 새로고침(세션 1 요약이 다시 보인다)한 뒤 `세션 시작`. 첫 질문을 확인하고, 아래 문장을 넣어 `보내기`, 이어서 `세션 종료`.
  > 캐시 서버는 트래픽이 적은 새벽에 한 대씩 재시작하고, 재시작 후 적중률을 확인합니다.
- 기대 결과: `세션 2/10`, 출처 `후임이 물어본 질문`, 질문은 단계 12의 문장 그대로. 보낸 뒤 `오늘 쌓인 것: 1항목`, 종료 요약 첫 줄 `담당 시스템: 캐시 서버는 트래픽이 적은 새벽에 …`.
- 스크린샷: `demo-17-leaver-successor-question.png` (첫 질문이 보이는 시점)

### 단계 18 — 후임 창 단계 12 질문 다시

- 행동: 질문 칸에 단계 12와 같은 문장을 넣고 `보내기`.
  > 캐시 서버를 재시작해야 할 때는 어떻게 하나요?
- 기대 결과: 이번에는 파란 상자. `인수인계 기록에 따르면: 캐시 서버는 트래픽이 적은 새벽에 한 대씩 재시작하고, 재시작 후 적중률을 확인합니다.` 근거 `세션 2 (담당 시스템)`, 확신도 `근거 확실`, 큐 적재 안내 없음.
- 스크린샷: `demo-18-successor-grounded-answer.png`

### 단계 19 — 후임 창 팀장 화면 열어 보기

- 행동: 후임 창 주소창에 `http://localhost:8780/report` 를 연다.
- 기대 결과: 빨간 상자 `이 화면을 볼 권한이 없습니다.` 축 막대·큐·빈 구멍이 비어 있고 버튼이 모두 꺼져 있다.
- 스크린샷: `demo-19-successor-report-forbidden.png`

### 단계 20 — 팀장 창 퇴사자 세션 깊이 API 직접 열기

- 행동: 퇴사자 창 개발자 도구 → Application → Local Storage 에서 `handoff.session.kim` 값(세션 ID)을 복사해, 팀장 창 주소창에 `http://localhost:8780/sessions/<세션 ID>/depth` 를 연다. (팀장은 이 경로 자체가 막혀 있어서 아무 ID로 열어도 결과가 같다.)
- 기대 결과: 응답 403, 본문 `{"detail":"forbidden"}`. 팀장은 답변 원문·답변별 깊이·지식 카드·훈련 결과를 볼 수 없다.
- 스크린샷: `demo-20-manager-depth-forbidden.png`

## 확인 포인트 정리

| 무엇을 | 어느 단계 |
|---|---|
| 팀장 우선 질문이 퇴사자 첫 질문으로 나오고 출처가 보인다 | 5 → 7 |
| 후임 답에 근거·확신도가 붙고 연락처는 `[전화번호]` 로 가려진다 | 11, 16 |
| 후임이 모르는 질문이 퇴사자 다음 세션 첫 질문이 되고, 답한 뒤 근거 있는 답으로 바뀐다 | 12 → 17 → 18 |
