# 케이스 스터디: 감시 도구가 되지 않는 인수인계

핸드오프는 퇴사자가 매일 15분 질문에 답하고, 그 답을 후임이 근거와 함께 찾아보고, 팀장은 비어 있는 영역만 보는 인수인계 도구다. 이 문서는 만들면서 내린 판단 세 가지를 "문제 → 판단 → 근거 → 결과" 순서로 적는다. 구조 그림은 [아키텍처](media/architecture.svg).

## 문제

- 퇴사자는 마지막 2주를 문서 한 장 쓰는 데 쓰고, 그 문서는 아무도 읽지 않는다. 정작 필요한 "왜 그렇게 했는지·어디가 함정인지·누구에게 물어야 하는지"는 문서에 없다.
- 그래서 질문하는 쪽이 끌어내는 방식을 택했다. 질문은 담당 시스템·반복 업무·사고 이력·관계자 네 축으로 깊어지고, 답은 검색 가능한 지식베이스가 된다.
- 그런데 답을 모으는 도구는 쉽게 감시 도구가 된다. 첫 통합 분석에서 실제로 그랬다: 인증이 없어 누구나 자료 원문·세션 요약을 읽을 수 있었고, 답변별 깊이와 훈련 결과가 누구에게나 열려 있었다. 검색에는 다른 퇴사자의 답이 섞였고, 답과 발췌에 전화번호·이메일 원문이 나왔다.
- 퇴사자가 "이 답이 나를 평가하는 데 쓰인다"고 느끼면 솔직하게 답하지 않는다. 감시가 되는 순간 인수인계 자체가 실패한다.

근거: 2026-10-23 역할 통합 전에 API 와 화면을 한꺼번에 점검했다. 인증이 없어 자료·카드·큐·세션 요약이 누구에게나 열려 있었고, 검색에 퇴사자 구분이 없었으며, 연락처 가리기는 카드에만 있었다. 문제 정의는 [README 문제·하지 않는 것](../README.md#하지-않는-것).

## 원칙: 감시 도구가 되지 않게

**판단 1 — 계정 대신 초대 링크.** 이름·이메일·비밀번호를 받지 않는다. 역할 하나와 퇴사자 id 하나를 서명한 초대 링크를 관리자가 직접 전달한다. 계정 DB 가 필요한 라이브러리와 별도 인증 서버는 개인정보 최소 수집에 맞지 않아 기각했다 (2026-10-23 역할 통합). 로그인 쿠키도 직접 서명하지 않고 Starlette `SessionMiddleware` 를 썼다.

**판단 2 — 팀장이 할 수 있는 개입은 "질문을 넣는 것"뿐.** 팀장은 커버리지·빈 구멍·모르는 영역·질문 큐 문구·산출물을 보지만 답변 원문·세션 요약·답변별 깊이·카드 목록·훈련 결과는 볼 수 없다. 우선 질문은 큐 맨 앞에 들어갈 뿐 답을 들여다보는 길이 아니다.

**판단 3 — 정책은 파일 하나, 빠진 경로는 거부.** (역할, 경로, 메서드) 허용 목록을 `policy.csv` 하나에 두고 모든 라우터에 같은 검사를 건다. 정책에 없는 경로, 본문에서 퇴사자 id 를 읽을 수 없는 요청은 거부한다(fail-closed). 앱의 모든 라우트가 정책 표에 있는지는 단위 테스트가 강제한다.

**판단 4 — 수치를 부풀리지 않는다.** 큐 질문에 답한 것을 질문 트리 주제에 억지로 매핑하지 않고 "추가 질문 N개 답함"으로 따로 보여 준다. 연락처는 지식베이스 적재 전과 응답 직전 두 번 가린다. 발급 권한과 데이터 열람 권한은 관리자·팀장으로 나눈다.

**원칙을 좁힌 한 번.** 2026-10-29 질문 대화 화면에서 팀장도 본인이 넣은 우선 질문의 답 원문만은 보게 했다. 질문한 사람이 답을 확인하는 것은 감시가 아니라 질문의 마무리라고 봤다. 대신 범위를 출처 `manager` 항목으로 좁혔고, 퇴사자 화면에는 이미 "팀장 우선 질문" 출처가 보여 퇴사자는 누가 보는지 알고 답한다.

**공개 데모도 같은 원칙.** 방문자마다 새 퇴사자 id 의 연습 공간을 만들어 기존 역할 검사가 그대로 격리를 맡는다. 답은 녹화본을 재생하고, 업로드는 막고, 요청 수에 상한을 둔다.

결과: 시연 시나리오의 마지막 두 단계가 이 원칙을 확인한다. 후임이 팀장 화면을 열면 권한 없음, 팀장이 세션 깊이 API 를 직접 열면 403 이다.

근거: 2026-10-23 역할 통합에서 초대 링크·정책 파일·fail-closed 검사를, 같은 날 포트폴리오 데모에서 방문자별 연습 공간과 관리자 역할 분리를 정했다. 2026-10-29 질문 대화 화면에서 팀장 예외를 본인 우선 질문으로만 열었다. 역할별로 볼 수 있는 것은 [README 하지 않는 것](../README.md#하지-않는-것)과 [사용 설명](usage.md), 확인 절차는 [시연 시나리오](demo-scenario.md).

## 버그: 후임 재질문 루프

**증상.** 후임이 넘긴 질문에 퇴사자가 답하고 세션을 마감해도, 후임이 같은 문장으로 다시 물으면 "없음"이 나오고 같은 질문이 큐에 또 쌓였다. 팀장 화면에는 같은 질문이 대기로 두 번 보였다. 질문 루프("모르면 퇴사자에게 다시 간다")가 닫히지 않는 것이라 제품의 핵심 약속이 깨진 셈이었다.

**원인.** 키 없이 도는 내장 공급자는 답 본문만 임베딩한다. 질문과 글자를 공유하지 않는 답은 벡터 검색에 걸리지 않았다.

**판단.** 검색 품질을 올리는 대신, 이미 있는 연결을 썼다. 큐 항목과 퇴사자 답은 항목 id 로 이어져 있다.
- 같은 문장(공백·끝 문장부호만 무시)이 답변된 후임 질문이면 그 항목에 연결된 마감 답을 근거 맨 앞에 둔다.
- 연결 답이 주장 검증에서 모두 빠지면 퇴사자 답 발췌 원문을 보여 준다. 바로 그 질문에 퇴사자가 한 답이라 지어낸 주장이 아니다.
- 이미 답변된 문장은 큐에 다시 쌓지 않는다. 큐 적재 SQL 은 다른 출처 항목의 의미까지 바꾸므로 건드리지 않았다.
- 기각한 대안: 임베딩에 질문을 같이 넣기, 바꿔 말한 질문까지 유사도로 맞추기. 둘 다 범위가 커서 뺐다.

**결과.** 서버 한 곳만 고쳤고 프론트와 팀장 화면은 그대로 뒀다. 프론트를 만들며 모아 둔 백엔드 이상 목록에서 이 항목을 닫았다. 다음 날 질문 대화 화면이 넘긴 질문의 답을 직접 보여 주면서 "다시 묻기" 버튼도 필요 없어졌다.

근거: 2026-10-28 수정. 원인은 질문 큐 중복 검사가 대기·질문 중 항목만 보고 답변된 항목은 보지 않은 것과, 내장 공급자가 답 본문만 임베딩한 것 두 가지였다. 바꿔 말한 질문은 지금도 벡터 검색만 탄다. 넘긴 질문이 돌아오는 흐름은 [시연 시나리오](demo-scenario.md).

## 품질 평가

**판단.** 품질은 규칙으로 잰다. 가상 퇴사자 고정 데이터로 10세션을 진행한 뒤 후임 질문 20개를 던지고 기대 주제·키워드로 판정한다. LLM 심판을 쓰지 않아 판정 자체가 흔들리지 않는다. 목표값·고정 데이터·테스트는 완화하지 않는다.

**MVP 결과.** 답변 있음 16/20, 근거 세션 맞음 14/14 였지만 지어낸 답이 2건이었다. 인수인계에 없는 주제(정산 배치 수동 복구·결제 대행사 장애 연락처)에 관련만 있는 근거로 답을 만들었다.

**대응.** 주장 단위 검증과 질문 상황 일치 판정을 넣었다. 지어낸 답은 보정 전 2건(q16·q17)에서 qwen 실측 1회차·2회차 모두 0 이 됐다.

**대가를 숨기지 않았다.** 검증이 보수적이라 답변 있음이 16/20 에서 12/20 으로 줄었고, 최장 세션이 6초에서 28초로 늘었다. LLM 은 실행마다 답이 달라서 같은 평가를 3회 돌려 평균으로 판정했다. 지어낸 답은 3회 모두 0 이지만, 정직성 지표 3개(fence_accuracy 0.733, routing 0.667, uncertain_detect 0.778)는 평균 미달이고 모든 목표를 동시에 충족한 회차는 0/3 이다. 원인은 진단해 문서에 남겼고 고치지 못한 것은 미달로 그대로 적었다.

## 배운 것

- "하지 않는 것"을 먼저 정하면 설계가 쉬워진다. 팀장 권한을 정할 때마다 "이게 감시가 되는가"라는 한 질문으로 판단했다.
- 원칙을 바꿀 때는 넓히지 않고 좁힌다. 팀장 원문 예외는 "본인이 낸 질문"으로만 열었고, 그 사실을 퇴사자 화면에서도 보이게 했다.
- 검색을 더 똑똑하게 만들기 전에 이미 있는 연결(큐 항목 id)을 본다. 재질문 버그는 임베딩을 바꾸지 않고 풀렸다.
- 지어낸 답을 없애면 답하는 양이 줄어든다. 그 대가를 수치로 같이 적어야 평가를 믿을 수 있다.
- 한 번 잰 LLM 평가는 표본 하나다. 여러 번 돌려 평균과 폭을 함께 본다.

근거: 위 세 절의 판단은 모두 작업 당시 날짜별 결정 기록에 대안과 기각 이유를 함께 남겨 두고 정리한 것이다. 수치는 [usage.md 평가 N회 집계](usage.md#평가-n회-집계).
